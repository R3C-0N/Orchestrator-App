## 1. But et problème d'origine

Remplacer l'interface terminal de Claude Code par une application de bureau qui pilote le CLI `claude` sans interface graphique, par le flux JSON (`stream-json`). L'application dessine elle-même la conversation, un panneau de sous-agents et, plus tard, des formulaires natifs.

Problème d'origine : l'interface terminal (TUI) de Claude Code sous Windows Terminal fige par moments et son défilement est inconfortable sur les longues sessions. Piloter le CLI par le flux JSON supprime la couche TUI : le rendu et le défilement deviennent ceux de notre application (liste virtualisée).

## 2. Décisions et conséquences

1. **Techno : Tauri 2, cœur Rust, interface web.** Le cœur Rust lance et supervise `claude.exe`, analyse le flux et expose des commandes et événements Tauri à l'interface. Conséquence : pas de Node obligatoire à l'exécution, donc pas de SDK TypeScript ; le protocole de contrôle est réimplémenté en Rust (voir section 5).
2. **Front : Svelte 5.** Conséquence : état de l'interface en runes (`$state`, `$derived`) ; un magasin par session reçoit les événements du cœur.
3. **Look : terminal pur.** Reproduire d'abord fidèlement le style terminal de Claude Code ; les modifications viendront après. Conséquence : police monospace, rendu par lignes et blocs, pas de bulles ni de cartes décoratives dans la conversation ; la fidélité au TUI est le critère de recette du prototype 1. Référence : la **vue normale** du TUI 2.1.325, capturée au jalon J1 (règles en section 2.1, inventaire et liste de contrôle dans `docs/reference-tui/README.md`) ; la vue détaillée (Ctrl+O) est reproduite aussi dans le prototype 1.
4. **Disposition : conversation + colonne des agents à droite**, elle aussi en style terminal : police mono, lignes de texte colorées par agent (bleu, vert, orange, violet, rose, cyan, jaune, rouge), d'après le `subagent_type` après `trim()`. Conséquence : une table couleur par nom d'agent (`agent-bleu` vers bleu, etc.) ; un agent inconnu reçoit une couleur neutre. La colonne reprend le style du panneau des agents du TUI 2.1.325 (`◯ <agent>  <description> … <durée> · ↓ <tokens> tokens`, capture `05-agents-en-cours`), qui s'affiche dans le TUI sous la ligne d'état.
5. **Périmètre du prototype 1 : « utilisable au quotidien »** (détail en section 6). Les formulaires natifs n'en font pas partie ; les questions de Claude (`AskUserQuestion`) sont néanmoins affichées dans une carte minimale (décision 6).
6. **Formulaires par étapes.** Prototype 1 : les questions de Claude (`AskUserQuestion`) sont affichées dans une **carte minimale en style terminal** : la question et ses options en liste, choisies au clavier (↑↓, Entrée) ou à la souris, avec un champ « autre réponse » libre (rendu du TUI, capture `07-question` : pas d'encadré, pastille « ☐ <header> », options `❯ 1. …`, « N. Type something. », « N+1. Chat about this », pied « Enter to select · ↑/↓ to navigate · Esc to cancel ») ; la réponse passe par `updatedInput.answers`, et la capacité `ask_user_question_unanswered_v1` sert à « ignorer ». Ce n'est pas un formulaire natif, et il n'y a pas d'aperçu HTML des options (reporté, voir section 7). Plus tard : un outil MCP « formulaire » fourni par l'app, qui remplacera le skill `formulaire-dynamique` en artefact. Conséquence : le prototype 1 doit gérer le `control_request` `can_use_tool` de `AskUserQuestion` (testé, section 4.5) ; l'outil MCP in-process nécessitera d'implémenter côté Rust le transport MCP sur le canal de contrôle (`mcp_message`), non étudié.
7. **Permissions : tout autoriser (`bypassPermissions`).** L'app reste branchée sur `--permission-prompt-tool=stdio` pour recevoir les `AskUserQuestion` et les éventuels `can_use_tool` restants. Conséquence : le gestionnaire de `control_request` existe dès le prototype 1, avec réponse `allow` par défaut pour tout ce qui n'est pas `AskUserQuestion`. Testé (`t8`) : le mode est accepté sans `--allow-dangerously-skip-permissions`, un Bash qui écrit dans le dossier de travail part sans `can_use_tool`, et `AskUserQuestion` arrive toujours en `control_request`. Les outils MCP marqués `requires_user_interaction` et certaines demandes (`default_to_no`, `safetyCheck`) peuvent rester soumis à demande (doc, non vérifié).
8. **Dépôt de développement : `H:\<user>\Code\orchestrator`**, branche `main`, avec le dépôt distant `origin` = `git@github.com:R3C-0N/Orchestrator-App.git` (GitHub, SSH). L'app est utilisée par plusieurs personnes : seul le propriétaire du dépôt GitHub (droit d'écriture) peut faire envoyer les améliorations, seulement leur branche `auto/…` et seulement vers ce dépôt canonique (décision 16) ; pour tous les autres, et pour tout fork ou miroir, l'app ne pousse jamais rien. Ce dépôt distant est aussi la source du clone que l'app fait d'elle-même (décision 16) ; ce clone n'a aucun lien avec le dépôt de développement.
9. **Reprise d'une session : tout l'historique est affiché, relu dans le transcript.** `--resume` ne réémet pas les tours passés sur stdout (`t7`) : l'app relit `~/.claude/projects/<dossier encodé>/<session_id>.jsonl` (voir 4.6). Conséquence : un lecteur de transcript isolé dans son propre module Rust (`sessions/transcript.rs`), tolérant (une ligne ou un type inconnu est ignoré et compté, sans rien bloquer), qui passe les lignes `user`/`assistant` du fil principal au même réducteur que le flux ; en cas d'échec, reprise sans historique affiché avec un avertissement. Le format est interne et non documenté : ce lecteur est **revérifié à chaque nouvelle version du CLI** (tests sur extraits anonymisés).
10. **Captures de référence du TUI : faites par un agent, validées par l'utilisateur.** Un agent lance Claude Code dans Windows Terminal (profil, police et taille fixés) et capture la fenêtre par script ; l'utilisateur valide ensuite les captures, et les captures ratées sont refaites. Conséquence : un script de capture versionné et une liste de 10 captures dans `docs/reference-tui/` (plan, jalon J1), avec une liste de contrôle par capture, qui sert de critère de fidélité (décision 3).
11. **Dossier de projet : argument au lancement, sinon sélecteur des projets récents.** `<app> .` ouvre le dossier courant, `<app> <chemin>` ce dossier ; sans argument, un sélecteur liste les projets récents lus dans `~/.claude/projects` (un sous-dossier par projet, trié par date du transcript le plus récent). Conséquence : le cœur doit retrouver le chemin réel d'un dossier encodé ; l'encodage n'est pas réversible (tout caractère hors `[A-Za-z0-9]` devient `-`), donc le chemin est lu dans le champ `cwd` des lignes du transcript le plus récent ; un dossier disparu est grisé.
12. **Version du CLI différente de 2.1.325 : avertir sans bloquer.** Un bandeau « version non testée » s'affiche (version lue dans la réponse à `initialize` puis dans `system/init`, notice `unexpected_version` émise une fois par le réducteur) ; l'app continue. L'avertissement peut être fermé (croix ✕ du bandeau, souris ou clavier) ; il revient au prochain changement de version (version fermée gardée dans le `localStorage` du webview, `src/lib/state/versionNotice.ts`). Les messages et types inconnus sont ignorés. Les mises à jour automatiques de Claude Code restent actives. Conséquence : le lecteur du flux et celui du transcript doivent être tolérants (variante `Unknown`), et les fixtures sont rejouées à chaque mise à jour du CLI pour repérer les ruptures.
13. **Raccourcis : comme Claude Code, d'après le comportement observé du TUI 2.1.325** (captures `c*`, `a*`, `n*`, `v*`, `k*`, `07`, `08`, `10` de `docs/reference-tui/README.md`). **Ctrl+C** : avec une sélection, il copie ; pendant un tour, il interrompt et **garde la saisie** (`c4`, `k2`) ; au repos avec une saisie non vide, il efface la saisie (`c2`) ; au repos avec une saisie vide, le TUI affiche « Press Ctrl-C again to exit » (`c3`), mais l'app **ne fait rien** (option la plus simple : l'app ne se quitte pas au clavier dans le prototype 1, pas de double Ctrl+C pour quitter). **Échap** : il ferme d'abord la palette ou le sélecteur ; sur une carte de question, il l'ignore si elle est ignorable (`can_skip`, capacité `ask_user_question_unanswered_v1` ; « Esc to cancel » dans le TUI, `07`), sinon il ne fait rien et la carte reste ; pendant un tour, il interrompt (`08`) ; au repos avec une saisie non vide, un premier appui affiche « Esc again to clear » **sans rien effacer**, et un second appui arrivé moins d'environ 0,8 s plus tard efface la saisie (mesuré : effacée à 736 ms, gardée à 843 ms ; captures `a000` à `a800` avant, `n000` à `n800` après) ; sur une saisie vide, deux appuis ouvrent le menu Rewind du TUI, aussi bien après un tour normal (`v1`) qu'après un tour interrompu (`v4`), et un appui de plus le referme (`v2`, `v5`) : **Rewind est hors du prototype 1**, donc l'app ne fait rien sur un double Échap à saisie vide. **`/`** en début de saisie ou **Ctrl+K** ouvre la palette, affichée au-dessus de la saisie (`10`) ; **Ctrl+O** bascule entre la vue normale et la vue détaillée. Conséquence : l'interruption passe toujours par le `control_request` `interrupt` (pas de signal sous Windows, voir 4.8) ; un gestionnaire de touches unique, testé cas par cas, tient compte de l'état (tour en cours, saisie vide ou non, sélection, palette, carte).
14. **Colonne des agents triée : en attente de réponse, puis en cours, puis terminés repliés.** Demande de l'utilisateur. Un agent « attend une réponse » quand la question ouverte (`AskUserQuestion`, seule demande soumise à l'utilisateur, décision 7) vient de son fil : l'événement `question` porte `thread` (`"main"` ou le `tool_use_id` de l'agent), retrouvé par le réducteur Rust d'après `agent_id` du `can_use_tool` (le `task_id` de l'agent) ou, à défaut, d'après le fil où l'appel `AskUserQuestion` a été vu ; une question du fil principal ne désigne aucun agent. Plusieurs questions peuvent attendre en même temps (fil principal et sous-agents) : elles sont en file, une par `request_id`, dans l'ordre d'arrivée (`SessionStore.questions`) ; la carte affiche la plus ancienne et la suivante paraît quand celle-ci est fermée, et tous les agents dont une question attend restent dans le groupe « en attente ». Les agents terminés, en échec ou arrêtés sont dans un panneau « ▸ N done » replié par défaut (clic, Entrée ou Espace) ; son état est gardé tant que l'app tourne. Conséquence : ordre de lancement dans chaque groupe (`groupAgents`, `agentView.ts`) ; un agent change de groupe en direct ; un agent en attente affiche `⎿  ☐ Waiting for your answer` en lavande (pastille de la carte de question, `07`) ; un agent dont le fil est déroulé quand il finit reste affiché sous l'en-tête replié jusqu'à ce que son fil soit refermé, et replier le panneau referme les fils des agents terminés ; un agent focalisé au clavier qui change de groupe garde le focus si sa carte reste affichée, sinon le focus passe à l'en-tête du panneau.
15. **Auto-amélioration : l'interface se recharge à chaud depuis un dossier local versionné** (demande de l'utilisateur, jalon J14). L'app modifie son propre code sans recompiler l'exe ni relancer : l'interface Svelte compilée est lue dans `%LOCALAPPDATA%\orchestrator\ui\<hash du commit>\` (pointeur `ui\active.json`), avec repli sur l'interface embarquée dans l'exe. Moyen : le fournisseur d'assets de Tauri est remplacé (`Context::set_assets`), donc l'origine reste `http://tauri.localhost` : capabilities, CSP et `localStorage` (décision 12) inchangés. Écarté : un protocole personnalisé (autre origine, `localStorage` perdu), `asset:` ou un serveur HTTP local (origine distante, ACL `remote` et CSP à élargir, port ouvert). Une version prête est activée **automatiquement dès que la session principale est au repos** (pas de tour en cours, pas de question ouverte) ; pendant un tour, l'app attend ; la saisie en cours, l'historique ↑↓ des envois et les agents dépliés sont conservés à travers le rechargement. La session (processus `claude.exe`, conversation, agents, questions) vit dans le cœur Rust et survit au rechargement : chaque session garde le journal de ses `CoreEvent` et l'historique repris, et l'interface rechargée s'y rattache et les rejoue (`attach_sessions`) au lieu de repartir de zéro. Conséquence : le rechargement ne ferme plus les sessions (le comportement « sessions orphelines fermées » du jalon J6 est remplacé par un détachement, puis une fermeture après 60 s sans rattachement) ; l'interface envoie un signal « prêt » (`ui_ready`) après son montage. Watchdog : après une bascule, une interface qui n'envoie pas `ui_ready` en 5 s est marquée fautive, et l'app revient à la précédente, puis à l'interface embarquée. Au démarrage, le délai est de 15 s : un premier échec sert l'interface embarquée pour cette exécution seulement, et la version n'est marquée fautive qu'au deuxième échec consécutif. Un `ui_ready` remet ce compteur à zéro. Une version active construite pour un autre contrat que celui de l'exe (exe réinstallé après une « relance requise ») n'est jamais servie : au démarrage, l'app revient à la précédente compatible, sinon à l'interface embarquée. Le cœur garde au plus une session principale : en lancer une nouvelle ferme l'ancienne (l'interface rechargée n'en reprendrait qu'une). L'app affiche le hash de l'interface qu'elle exécute. Les dossiers d'interface sont écrits de façon atomique (dossier temporaire, manifeste SHA-256, renommage) ; on garde la version active, la précédente et les 5 plus récentes valides.
16. **Le dépôt source de l'app est un clone fait par l'app elle-même.** Au premier lancement, l'app clone `origin` = `git@github.com:R3C-0N/Orchestrator-App.git` (SSH, clé de l'utilisateur) : dans le dossier d'installation s'il est accessible en écriture (installeur NSIS par utilisateur), sinon dans `%LOCALAPPDATA%\orchestrator\repo` (MSI dans Program Files). L'URL est compilée dans l'exe et remplaçable dans `%LOCALAPPDATA%\orchestrator\config.json`. Le clone est placé sur **le commit à partir duquel l'exe a été compilé** (hash injecté au build), pas sur la tête de `origin/main` : le contrat entre l'interface et le cœur reste cohérent. Le clone n'a aucun lien avec le dépôt de développement (décision 8) ; les améliorations sont fusionnées dans le `main` du clone, et son URL de push reste `no-push://` (la session dédiée ne pousse jamais). **App multi-utilisateurs, envoi réservé au propriétaire** : les autres utilisateurs ne modifient que leur clone local ; rien ne change pour eux. L'envoi est activé par `"push": true` dans `%LOCALAPPDATA%\orchestrator\config.json` (absent ou faux par défaut ; jamais exposé ni activable dans l'interface), la seule destination possible est le dépôt canonique compilé `git@github.com:R3C-0N/Orchestrator-App.git` (formes équivalentes acceptées : `git@github.com:R3C-0N/Orchestrator-App.git` et `ssh://git@github.com/R3C-0N/Orchestrator-App.git`, casse comprise ; rien d'autre) : si `repo_url` ou l'URL d'origine du clone (`remote.origin.url`, vérifiée au démarrage et avant chaque envoi) désigne un autre dépôt, l'envoi est désactivé avec la raison (le clone depuis un autre `repo_url`, miroir ou dépôt local, reste possible ; les forks ne sont pas concernés par l'envoi). L'autorité est GitHub : au démarrage (clone prêt) et avant chaque envoi, le cœur vérifie le droit d'écriture sur ce dépôt par `git push --dry-run <url> <commit>:refs/heads/orchestrator-sonde-ecriture-<aléa>` (la connexion au service `receive-pack` est authentifiée, GitHub la refuse sans droit d'écriture ; rien n'est écrit). Sans droit, l'envoi est désactivé et la raison est lisible dans `get_ui_info` (`push`) ; le réglage est ignoré. Avec droit, c'est le **pipeline** qui pousse, jamais la session : après une fusion réussie (cycle normal, « relance requise », retour arrière), après l'arrêt effectif de la session et les contrôles, il envoie **seulement la branche `auto/…`** vers le même nom distant (`<commit>:refs/heads/auto/…`), jamais `main`, jamais en force, jamais de suppression, vers l'URL réelle passée en argument, avec les identifiants de l'utilisateur, sans hooks ni invite, dans un Job Object avec délai. Ce que la sonde et l'envoi lisent, honnêtement. **Coupé** : la configuration git globale et système (`GIT_CONFIG_GLOBAL` = fichier vide de l'app, vidé avant chaque commande ; `GIT_CONFIG_NOSYSTEM=1` ; donc ni `pushInsteadOf` ni `credential.helper` de `~/.gitconfig`), `~/.ssh/config` (`ssh -F <fichier vide de l'app>` et `-o HostName=github.com -o User=git -o Port=22 -o ProxyCommand=none -o ProxyJump=none -o BatchMode=yes -o StrictHostKeyChecking=yes`, avec délais de connexion), les variables git et ssh héritées (`GIT_CONFIG_*`, `GIT_SSH*`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`, `GIT_SSL_*`, `GIT_TRACE*`…), y compris pour les lectures du clone faites avant l'envoi ; `safe.directory` = le clone. `git.exe` et `ssh.exe` sont résolus en chemins absolus une seule fois au lancement de l'app. Les `IdentityFile` de `~/.ssh/config` qui s'appliquent à `github.com` (blocs `Host`, sans évaluer `Match` ni `Include`) sont relevés une seule fois au lancement et passés en `-o 'IdentityFile="…"' -o IdentitiesOnly=yes` (guillemets doubles : un chemin avec une espace reste une seule valeur) ; sans eux, clés par défaut et agent ssh. **Reste lu** : `~/.ssh/known_hosts`, les clés par défaut (`~/.ssh/id_*`) et l'agent ssh, le `PATH` tel qu'il est au lancement de l'app (un `setx PATH` fait par une session joue à la relance suivante), le `.git/config` du clone (contrôlé à part, ci-dessous). Seul un compte Windows dédié à la session apporterait une garantie : c'est à l'utilisateur de trancher. Juste avant la sonde et l'envoi, la configuration locale du clone est relue : réécriture d'URL, `core.sshCommand`, `core.hooksPath`, `core.fsmonitor`, `core.askPass`, `core.gitProxy`, inclusions, identifiants, `http.proxy`, `http.extraHeader`, `http.sslVerify`, `http.sslCAInfo` (y compris par URL), `protocol.*`, et tout `remote.*` autre que `remote.origin.url`, `remote.origin.fetch` et `remote.origin.pushurl` désactivent l'envoi. Un échec d'envoi laisse la fusion locale acquise : le bandeau affiche « fusionné localement, envoi échoué : <raison> », la branche est mise en attente (liste tenue en mémoire par l'app, recopiée dans `%LOCALAPPDATA%\orchestrator\work\push-pending.json`, relue seulement au lancement) et renvoyée au cycle suivant et au démarrage suivant. Une fusion faite pendant la sonde ou après une sonde impossible (réseau) est mise en attente aussi, et la sonde est refaite au cycle suivant ; seul un refus définitif (pas de droit d'écriture, autre dépôt, réglage git refusé) ne met rien en attente. Si le clonage échoue (git absent, pas de réseau, pas de clé), la commande `/ameliorer` est désactivée et la raison est affichée ; le reste de l'app fonctionne.
17. **Cycle d'une amélioration.** L'utilisateur tape `/ameliorer <demande>` (entrée locale de la palette). Le cœur crée une branche `auto/<AAAAMMJJ-HHMM>-<sujet>` dans un `git worktree` du clone (jamais dans un arbre où l'utilisateur travaille) et y lance une session `claude.exe` dédiée, avec un prompt versionné dans le dépôt. Claude modifie et commite les seuls fichiers touchés ; le reste est fait par le cœur, de façon déterministe : contrôle (arbre propre, commits sur la branche, fichiers dans `src/`, `src-tauri/`, `e2e/`, `docs/`, `tools/`), **tests obligatoires** (`npm run check`, `npm test`, e2e de démarrage), build de l'interface étiquetée par le hash du commit, bascule, signal « prêt » sous 5 s, puis fusion **fast-forward** (`--ff-only`) dans le `main` du clone. Échec à une étape : retour automatique à la version précédente, branche laissée non fusionnée pour inspection. Retour arrière depuis un menu de l'app : réactivation immédiate de la version précédente, puis `git revert` passé par le même cycle. Chaque version d'interface est un commit. Harnais protégé : les tests passent dans un worktree jetable où les tests existants (`e2e/`, `src-tauri/tests/`) et le harnais (`tools/self-improve/`, `tools/contract-fingerprint.mjs`, `src-tauri/src/selfupdate/`, `src-tauri/.cargo/`, `src-tauri/build.rs` ; ces deux derniers parce que des `rustflags` ou un script de build pourraient empêcher les tests restaurés de s'exécuter, si bien qu'une nouvelle commande IPC se déclare à la main dans le dépôt de développement) sont restaurés depuis `base` (le `main` du clone au début du cycle) ; une amélioration qui modifie ou supprime un fichier protégé, ou qui ajoute un marqueur de test désactivé ou isolé dans une ligne d'un fichier de code, test ou code applicatif, est refusée. Marqueurs : dans un fichier JS/TS (`.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.svelte`), les méthodes `skip`, `only`, `fixme`, `todo`, `skipIf`, `runIf`, `fails` sous la forme `.nom(` (espaces permis avant la parenthèse), `` .nom` ``, `.nom.each` (et autres suites) ou `["nom"]` / `['nom']`, les fonctions `xit(`, `xtest(`, `xdescribe(` (limite de mot : `exit(` passe), et `test.fail`, `describe.skip` ; dans un `.rs`, sans tenir compte des espaces, `#[ignore` (donc `#[ignore = "…"]`), `cfg(any())`, `cfg(FALSE)`, `cfg(false)`, `cfg(not(all()))`, `cfg_attr(…, ignore)` ; dans un `Cargo.toml`, `autotests`, `autobins`, `autobenches`, `test = false`, `harness`, `doctest` (le reste du manifeste, dont les dépendances, reste modifiable). La documentation et les autres fichiers non-code ne sont pas concernés : la spec cite ces marqueurs. Les tests unitaires du cœur (`#[cfg(test)]` dans `src-tauri/src/`, hors `selfupdate/`) ne sont pas restaurés : ils vivent dans le même fichier que le code qu'ils testent, et les restaurer reviendrait à annuler la modification ; seuls les marqueurs les protègent, et une session peut encore affaiblir ou retirer un test unitaire existant sans être détectée. Un nouveau fichier de test est permis et s'exécute en plus. Après la fusion, et pour le seul propriétaire, le cœur envoie la branche `auto/…` (décision 16) ; la session dédiée, elle, n'a toujours aucun moyen prévu de pousser (parades ci-dessous, inchangées). Promesse tenue : **pas de push involontaire, ni par les formes testées** ; ce n'est pas une isolation. La session garde les droits Windows de l'utilisateur (clés SSH de `~/.ssh`, gestionnaire d'identifiants Windows, configuration de `gh`, accès réseau) : une session qui chercherait délibérément à pousser le pourrait (lire une clé et appeler `ssh -i`, demander un identifiant au gestionnaire, faire du HTTP pur avec node ou python, défaire son environnement avec `env -u`, `set VAR=` sous cmd ou `Remove-Item Env:` sous PowerShell). Seule une exécution sous un autre compte Windows ou dans un bac à sable sans les identifiants de l'utilisateur offrirait une garantie ; **c'est à l'utilisateur de trancher** (un clone jetable sans remote n'en est pas une : la session a toujours accès aux mêmes identifiants et au réseau). Parades en place, à deux niveaux. (1) Filtre sur le texte des commandes (`--disallowedTools`, jokers compris, refus tenus en `bypassPermissions`) : `git push`, `git -C … push`, `git --… push`, `git -c`, `git.exe`, `git credential`, `credential-manager`, `git --config-env`, `GIT_CONFIG_PARAMETERS`, `GIT_ALLOW_PROTOCOL`, `git remote`, `git config`, `git submodule`, `git worktree`, `git update-ref`, `git branch -f`, `gh`, `ssh`, `curl`, et les questions (un message de commit qui contient « push » passe par `git commit -F`). Ce filtre ne voit pas une commande lancée par un autre programme (`cmd /c`, `node -e`, script). (2) Environnement de tous ses processus : **liste blanche** des variables héritées (système, dossiers de l'utilisateur, authentification de l'API par `ANTHROPIC_*` ou `USERPROFILE`, mandataire ; ni jeton ni agent SSH), aucun transport git permis (`protocol.allow=never`), toute URL de push réécrite en `no-push://`, pas de configuration git système ni globale, pas d'invite ni d'aide à la saisie, SSH coupé, sans hooks. Vérifié en réel (haiku) : `git -C . push`, `git -c … push`, `git --config-env … push`, `GIT_CONFIG_PARAMETERS=… git push`, `GIT_ALLOW_PROTOCOL=… git push`, `git credential fill`, `git credential-manager get` refusés ; `cmd /c git push`, `node -e` qui lance `git push`, push vers une URL SSH, HTTPS, `file://` ou un chemin local en échec ; jeton et variable privée de l'app absents de la session ; `git commit -m "…push…"` et `git grep push` permis. Non testé : `git credential-manager` appelé par un autre programme, `ssh -i` avec une clé de l'utilisateur, HTTP pur (node, python), `VAR=x git push` pour d'autres variables que les deux refusées. Après la session, `.git/config` (mis en lecture seule pendant la session, attribut que git pour Windows contourne ; verrou `.git\improve-active` posé pendant la session, et au démarrage suivant un verrou resté après un arrêt brutal fait retirer l'attribut) est comparé, après l'arrêt effectif de la session, en contenu, taille et date : toute modification, même annulée, refuse le cycle. Fichiers hors du worktree que la session peut atteindre avec le compte de l'utilisateur, et ce qui en est contrôlé : `%LOCALAPPDATA%\orchestrator\config.json` (empreinte SHA-256 prise au lancement de l'app ; s'il a changé après une session, le cycle est refusé avec la raison) ; `%LOCALAPPDATA%\orchestrator\work\push-pending.json` (la liste fait foi en mémoire ; s'il diffère après une session, le cycle est refusé et le fichier rétabli, et une entrée ajoutée n'est jamais envoyée ; une entrée n'est de toute façon envoyée que si son commit est dans le `main` du clone) ; `.git/config` et les hooks du clone (contrôlés, voir plus haut) ; `~/.gitconfig` et la configuration système de git (pas lus par la sonde ni par l'envoi) ; `~/.ssh/config` (pas lu par l'envoi ; seuls ses `IdentityFile` pour `github.com` sont relevés au lancement de l'app, donc une modification faite par une session n'agit qu'après une relance, et seulement sur le choix de la clé). Les fichiers de l'app sont contrôlés et rétablis après l'arrêt de la session, même si elle échoue ou est annulée ; `config.json` est aussi contrôlé avant de lancer la session. **Non contrôlés** : les clés (`~/.ssh/*`), `~/.ssh/known_hosts` (gardé pour vérifier la clé de GitHub ; une session pourrait y remplacer la clé d'hôte, ce qui ne servirait qu'avec un serveur joignable sous le nom `github.com`), le gestionnaire d'identifiants Windows et la configuration de `gh`. Restent aussi atteignables par la session et lus à l'envoi suivant : le `PATH` de l'utilisateur (pris en compte à la relance de l'app) et `~/.ssh/known_hosts`. Face à une session qui tourne sous le même compte Windows, seul un compte Windows dédié apporterait une garantie : c'est à l'utilisateur de trancher. Conséquence : une interface n'est chargée que depuis le dossier local de l'app (elle a accès aux commandes IPC) ; un autre processus de l'utilisateur pourrait l'écrire, mais il a déjà les mêmes droits que l'app. Le manifeste SHA-256 protège contre une version incomplète ou corrompue (arrêt brutal, disque, antivirus), pas contre une modification volontaire : il est écrit dans le même dossier que les fichiers qu'il décrit. Un processus de l'utilisateur qui peut écrire dans `%LOCALAPPDATA%\orchestrator\ui\` peut aussi récrire le manifeste. Ce n'est donc pas une garantie d'authenticité. Même limite au démarrage : l'app lit le PATH utilisateur et machine du registre et exécute `--version` sur les candidats trouvés (git, Node, npm, cargo, et `node_path` / `cargo_path` de `config.json`, chemins absolus seulement). Un dossier du PATH accessible en écriture permet donc d'exécuter un programme dès le lancement ; c'est un risque déjà connu sous Windows, que l'app ne réduit pas.
18. **Cœur Rust : pas de remplacement à chaud.** Une amélioration qui touche `src-tauri/`, `package.json` ou `tauri.conf.json`, ou qui change l'empreinte du contrat (liaisons `src/lib/core/bindings/`, `capabilities/default.json`, `build.rs`), suit le même chemin git mais n'est **jamais activée** sur l'exe en cours (elle appellerait des commandes absentes) : elle est fusionnée après les tests Rust et marquée « relance requise ». La recompilation et la réinstallation de l'exe sont faites à la main. Reprise de la session au lancement suivant (`--resume`) : prévue, non implémentée au prototype 1 (J15). Les réglages surveillés et appliqués à chaud (thème, raccourcis, palette, skills affichés) sont un jalon à part (J15).
19. **Dépendances à l'exécution pour s'améliorer.** La décision 1 tient pour l'usage normal : aucun Node n'est requis pour converser. L'auto-amélioration demande en plus git, Node et npm (tests et build de l'interface), cargo (tests d'une modification Rust) et un accès SSH au dépôt distant pour le premier clone. Si l'un manque, la fonction est désactivée proprement, avec la raison, sans effet sur le reste de l'app. Ces outils ne sont pas lancés par leur nom nu (PATH hérité périmé, Node derrière le lien de nvm pour Windows que Windows peut refuser de traverser) : l'app les résout (`selfupdate/tools.rs`) par les réglages `node_path` et `cargo_path` de `config.json` (prioritaires, fichier ou dossier), le PATH du processus, le PATH utilisateur et machine du registre, puis nvm (`NVM_SYMLINK`, sa cible, `NVM_HOME*`) et `~/.cargo/bin`, et ne retient qu'un candidat qui répond à `--version`. Les quatre outils sont vérifiés et la raison les cite tous avec l'erreur réelle (« Node : lancement refusé (…) ; cargo : introuvable »). Les dossiers de Node et de cargo passent en tête du PATH des sous-processus et de la session d'amélioration. Au démarrage, l'app lit le PATH utilisateur et machine du registre et exécute `--version` sur les candidats trouvés et sur `node_path` / `cargo_path` ; les entrées relatives sont ignorées. Un dossier du PATH accessible en écriture permet donc d'exécuter un programme dès le lancement (risque déjà connu sous Windows, voir la décision 17). git est lancé par son chemin résolu pour tout le pipeline ; l'envoi (décision 16) garde son git et son ssh résolus à part, dans un environnement isolé.

## 3. Architecture

```
[ Interface Svelte 5 ]  <-- événements Tauri / commandes -->  [ Cœur Rust ]  <-- stdin/stdout NDJSON -->  [ claude.exe ]
 liste virtualisée, panneau agents,                           spawn, lecture ligne à ligne,              session longue,
 palette Ctrl+K, saisie                                       enums serde, corrélation des               outils, sous-agents,
                                                              control_request                            skills, hooks, MCP
```

- **Un processus `claude.exe` par session**, qui reste ouvert tant que stdin est ouvert. Le cœur Rust écrit un message utilisateur JSON par ligne sur stdin et lit un événement JSON par ligne sur stdout.
- **Cœur Rust** : lancement, lecture robuste (certaines lignes font plusieurs ko), désérialisation en enums, table des sous-agents (`tool_use_id`), table des `control_request` en attente (par `request_id`), envoi de `control_response` et de `control_request` (interrupt, set_model). Il transmet à l'interface des événements déjà normalisés.
- **Interface Svelte** : conversation en liste virtualisée alimentée par les deltas de texte, colonne des agents, palette de skills, sélecteur de sessions.
- Répertoire de travail du processus = dossier du projet ouvert ; `claude` y charge ses skills, agents, hooks et MCP comme en interactif (sauf `--bare`).

### 4.1 Commande de lancement

```
claude.exe -p --input-format stream-json --output-format stream-json --verbose ^
  --include-partial-messages --forward-subagent-text ^
  --permission-mode bypassPermissions --permission-prompt-tool stdio
```

Options testées (une par une dans les fixtures) :

| `--include-partial-messages` | deltas `stream_event` (`text_delta`, `input_json_delta`) | `t1`, `t6` |
| `--replay-user-messages` | ré-émet les messages utilisateur envoyés sur stdin, `"isReplay":true`, avec `uuid` | `t1` |

Le SDK documente `allowDangerouslySkipPermissions` comme requis ; le CLI brut ne l'exige pas pour ce test (une note de doc distincte du CLI est à surveiller aux mises à jour).

### 4.2 Message utilisateur (stdin)

Une ligne JSON par message :

```json
{"type":"user","message":{"role":"user","content":"Dis bonjour en un mot."}}
```

Un message commençant par `/nom-de-skill args` invoque le skill (testé avec `/orchestrateur`, `t5`). Le processus reste ouvert entre deux tours (testé, `t1`) ; il se termine à la fermeture de stdin.

### 4.3 Événements émis (stdout)

Séquence typique d'un tour (`t1`) : `system/hook_started`, `system/hook_response`, `system/init`, `system/status`, `user` (replay), `stream_event`*, `assistant`, `rate_limit_event`, `result`.

- `system/init` : `session_id`, `model`, `permissionMode`, `cwd`, `tools`, `mcp_servers` (`{name,status,source}`), `slash_commands`, `skills`, `agents`, `plugins`, `capabilities` (19 chaînes, test de fonctionnalités), `claude_code_version`. **Il n'est émis qu'après le premier message utilisateur** (`t12` : processus lancé sans message utilisateur, puis stdin fermé ; la capture ne contient que des `hook_*`, aucun `init` ; elle n'est pas horodatée, aucune durée n'est donc affirmée) **puis de nouveau à chaque tour** (`t1` : 2 `init` pour 2 `result` ; `t5` : 3 pour 3). Pour remplir la palette de skills (Ctrl+K) avant le premier message, deux sources : la requête de contrôle `initialize` (voir 4.7bis, testée, `t11`) ou, à défaut, une lecture de `~/.claude/skills`, `~/.claude/agents` et des plugins ; `init` complète ensuite (états MCP, outils, modèle).
- `system/status` : `{"status":"requesting"}` au début de chaque requête API.
- `stream_event` : enveloppe de l'API Messages, `event.type` parmi `message_start`, `content_block_start`, `content_block_delta` (`text_delta`, `input_json_delta` avec `partial_json`), `content_block_stop`, `message_delta`, `message_stop` ; porte `parent_tool_use_id` et `uuid`.
- `assistant` : message complet ; blocs `text`, `thinking` (contenu vide, signature seule), `tool_use` (`id`, `name`, `input`).
- `user` avec `tool_result` : `{"tool_use_id":"…","type":"tool_result","content":"…"}`.
- `result` : `subtype` (`success`, `error_during_execution`), `is_error`, `terminal_reason` (`completed`, `aborted_streaming`), `result` (texte), `total_cost_usd`, `duration_ms`, `duration_api_ms`, `num_turns`, `usage`, `modelUsage` (avec `contextWindow`), `permission_denials`, `subagent_stats`.
- `rate_limit_event` : `rate_limit_info` (statut, fenêtres d'utilisation).
- Autres `system/*` observés : `thinking_tokens`, `task_started`, `task_progress`, `task_updated`, `task_notification`, `background_tasks_changed`. Décrits par la doc ou le SDK, non capturés : `api_retry`, `permission_denied`, `plugin_install`, `control_request_progress`, `prompt_suggestion`.

### 4.4 Sous-agents (`t3`)

- L'appel : un `assistant` du fil principal avec un `tool_use` de nom **`Agent`** (`input.subagent_type`, `description`, `prompt`, `run_in_background`). Vérifié : dans `t3`, les 2 `tool_use` ont `"name":"Agent"`, alors que `init.tools` (`t1`, `t3`, `t5`, `t8`) liste **`Task`** et jamais `Agent`. `sdk.d.ts` ne liste que `Agent` dans `BUILTIN_TOOL_NAMES` : `Task` est l'ancien nom, resté dans la liste d'outils de l'`init`. L'app doit reconnaître **les deux noms** (`Agent` et `Task`) dans un `tool_use` ; seul `Agent` a été observé dans le flux.
- `system/task_started` : `task_id`, `run_id`, **`tool_use_id`** (= id du `tool_use` Agent, clé de liaison), `description`, `subagent_type`, `is_backgrounded`, `spawn_depth`, `task_type`, `prompt`.
- Messages du sous-agent : `assistant` et `user` avec `parent_tool_use_id` = id du `tool_use` Agent (les messages du fil principal ont `null`). Les sous-agents imbriqués portent l'id de l'Agent ou du Skill parent (doc, non testé).
- `system/task_progress` : `description`, `usage:{total_tokens,tool_uses,duration_ms}`, `last_tool_name` (source de « outil en cours »).
- Fin : `system/task_updated` (`patch:{status:"completed",end_time}`) puis `system/task_notification` (`status`, `summary`, `output_file`, `usage`). Un sous-agent d'avant-plan renvoie en plus un `tool_result` au fil principal.
- Arrière-plan : `run_in_background:true` ; `tool_result` immédiat « Async agent launched » ; `system/background_tasks_changed` donne la liste des tâches actives (`tasks:[]` à la fin).
- Parallélisme : plusieurs sous-agents s'entrelacent dans le flux ; on les distingue par `parent_tool_use_id` / `tool_use_id`.
- Skill forké lancé par `/skill` : messages avec `parent_tool_use_id` préfixé `forked-command-`, arrivant groupés après coup (doc, non testé).
- Couleur : `subagent_type.trim()` (voir pièges).

### 4.5 Protocole de contrôle

Enveloppes (types : `SDKControlRequest`, `SDKControlResponse` dans `.claude-work/reference/sdk.d.ts`) :

```json
{"type":"control_request","request_id":"<id>","request":{"subtype":"…"}}
{"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{…}}}
```

Le CLI et l'app peuvent chacun émettre des `control_request`, chacun répond par un `control_response` au même `request_id`. Un `control_cancel_request` annule une demande en attente (par exemple un `can_use_tool` après un interrupt).

**Permission, CLI vers app (`t4`)**

```json
{"type":"control_request","request_id":"bda218c7-…","request":{"subtype":"can_use_tool","tool_name":"Bash","input":{"command":"echo salut > b.txt","description":"…"},"description":"…","permission_suggestions":[{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"echo salut *"}],"behavior":"allow","destination":"localSettings"}],"blocked_path":"…","tool_use_id":"toolu_019Sj…"}}
```

Réponse (testée, accepte) :

```json
{"type":"control_response","response":{"subtype":"success","request_id":"bda218c7-…","response":{"behavior":"allow","updatedInput":{"command":"echo salut > b.txt","description":"…"}}}}
```

Refus (capturé, `t9`, mode `default`) : réponse `{"behavior":"deny","message":"Refusé par l'utilisateur (test)"}`. Claude reçoit un `tool_result` d'erreur portant ce message (`{"type":"tool_result","content":"Refusé par l'utilisateur (test)","is_error":true,"tool_use_id":"toolu_013u…"}`), l'outil ne s'exécute pas (le fichier n'est pas créé), le tour continue (`result` `success`, texte « refusé ») et `result.permission_denials` liste l'appel : `[{"tool_name":"Bash","tool_use_id":"toolu_013u…","tool_input":{"command":"echo deux > d.txt",…}}]`. Champ optionnel `interrupt` du refus défini dans `sdk.d.ts` (`PermissionResult`), non testé. « Toujours autoriser » : renvoyer une suggestion dans `updatedPermissions`. Champs utiles de la demande : `tool_use_id`, `agent_id`, `decision_reason`, `requires_user_interaction`, `default_to_no`.

**AskUserQuestion, CLI vers app (`t4`)** : même `can_use_tool` avec `tool_name:"AskUserQuestion"` et `requires_user_interaction:true`.

```json
"input":{"questions":[{"question":"Quelle est ta couleur préférée ?","header":"Couleur","options":[{"label":"Rouge","description":"Rouge"},{"label":"Bleu","description":"Bleu"}],"multiSelect":false}]}
```

Réponse (testée) : `allow` avec `updatedInput` = `questions` recopiées + `answers` (clé = texte de la question, valeur = label choisi) :

```json
{"behavior":"allow","updatedInput":{"questions":[…],"answers":{"Quelle est ta couleur préférée ?":"Bleu"}}}
```

Selon la doc : multi-sélection = tableau de labels (ou labels joints par `", "`) ; **vérifié en réel** (`t16`, finitions) : le tableau `["Rouge","Bleu"]` est accepté et Claude reçoit `"Quelles couleurs ?"="Rouge,Bleu"` (labels joints par `,` sans espace) ; texte libre (champ « autre réponse ») = le texte tapé devient la valeur ; `response` optionnel pour une réponse libre globale ; 1 à 4 questions, 2 à 4 options, `header` de 12 caractères au plus ; `preview` par option seulement si l'option SDK `toolConfig.askUserQuestion.previewFormat` est réglée (hors prototype 1, voir section 7). Non disponible dans les sous-agents. L'outil n'est offert à Claude qu'avec `--permission-prompt-tool stdio` (absent de `init.tools` sans hôte, présent dans `t5` et `t8`).

**« Ignorer » une question (`t10`, testé).** Capacité `ask_user_question_unanswered_v1` (dans `init.capabilities`) : la réponse peut porter `annotations[<texte de la question>].unanswered` parmi `skipped`, `replied_in_chat`, `dismissed` (`sdk.d.ts`). À n'envoyer qu'à un CLI qui annonce la capacité. Réponse testée :

```json
{"behavior":"allow","updatedInput":{"questions":[…],"answers":{},"annotations":{"Quelle est ta couleur préférée ?":{"unanswered":"skipped"}}}}
```

Claude reçoit `{"type":"tool_result","content":"The user did not answer the questions."}` et le dit dans sa réponse. Même texte, vérifié en réel, pour `replied_in_chat` (`t17`, envoyé par « Chat about this ») et `dismissed` (`t18`) : en 2.1.325 la raison ne figure pas dans le `tool_result`.

**Interrompre (`t6`)**

```json
{"type":"control_request","request_id":"int-2","request":{"subtype":"interrupt"}}
```

Réponse : `{"subtype":"success","request_id":"int-2","response":{"still_queued":[]}}`. Le tour se termine par un `result` `error_during_execution` / `aborted_streaming` et un message `user` « [Request interrupted by user] » ; la session reste utilisable. Option `cancel_queued:true`.

**Changer de modèle (`t5`)**

```json
{"type":"control_request","request_id":"mdl-1","request":{"subtype":"set_model","model":"sonnet"}}
```

Réponse : `{"response":{"model":"claude-sonnet-5-5"}}`. Le tour suivant utilise le nouveau modèle.

**Autres requêtes de contrôle** (définies dans `sdk.d.ts`, non testées) : `set_permission_mode`, `set_max_thinking_tokens`, `stop_task` (arrêter un sous-agent), `get_context_usage`, `get_session_cost`, `mcp_status`, `mcp_toggle`, `rewind_files`, `rename_session`, `reload_plugins`, `reload_skills`, `initialize`, `background_tasks`, `request_user_dialog`, `mcp_message`, `hook_callback`.

### 4.6 Reprise de session

`--resume <session_id>` recharge le contexte (`t7`) et garde le même `session_id`. Le CLI accepte aussi un nom de session ou le chemin d'un `.jsonl`, mais **l'app n'accepte que l'UUID** pour `resume` : c'est une règle de l'app (`validate_launch_options`, `src-tauri/src/process/spawn.rs`), qui renvoie `InvalidArgument` pour toute autre forme. `--fork-session` en crée un nouveau ; `--session-id <uuid>` impose l'id. La liste des sessions du prototype 1 se lit dans les transcripts du CLI, `~/.claude/projects/<dossier encodé>/<session_id>.jsonl` (constaté sur la machine). `--resume` ne réémet pas les tours passés sur stdout (`t7`) : l'historique affiché est relu dans le transcript (décision 9).

### 4.7 Skills, agents, hooks, MCP

Chargés en `-p` comme en interactif, sauf avec `--bare` ou `--safe-mode` (doc headless, et `t1` : skills personnels, agents `agent-*` et hook SessionStart présents). Les serveurs MCP apparaissent dans `init.mcp_servers` avec un statut (`pending`, `connected`, `needs-auth`, `failed`) ; la plupart sont `pending` à l'init.

### 4.7bis Requête `initialize` avant le premier message (`t11`)

Envoyée juste après le lancement, sans message utilisateur : `{"type":"control_request","request_id":"init-1","request":{"subtype":"initialize"}}`. Le CLI répond (testé) par un `control_response` `success` dont `response` contient notamment `commands` (108, avec `name`, `description`, `argumentHint`), `agents` (22), `models` (`value`, `resolvedModel`, `displayName`, `supportedEffortLevels`…), `output_style`, `account`, `claude_code_version`, `current_permission_mode`, `session_state`, `capabilities`, `pid`. Aucun `system/init` n'est émis à ce stade. Cela donne la palette de skills et la liste des modèles sans attendre le premier tour. Les champs `account.email` et `account.organization` sont masqués dans la fixture.

### 4.8 Pièges

- **`subagent_type` entouré de U+00A0** : le flux donne `"\u00a0agent-bleu\u00a0"` (octets `C2 A0` autour du nom, relevés avec `od -c` dans `t3` ; la liste `init.agents` a la même forme). La source est le frontmatter des agents (`name: "\u00a0agent-bleu\u00a0"` dans `~/.claude/agents/agent-bleu.md`) : ce ne sont donc pas des espaces ordinaires. Toujours `trim()` avant comparaison ou couleur : `str::trim` de Rust et `String.prototype.trim` de JavaScript retirent U+00A0 (propriété Unicode White_Space). Ne pas utiliser un `trim` ASCII. (Dans l'`input` du `tool_use`, la valeur est `agent-bleu`, sans ces caractères.)
- **`system/init` n'arrive qu'après le premier message, puis à chaque tour** (voir 4.3) : ne pas réinitialiser l'interface à chaque `init`, et ne pas attendre un `init` pour afficher la palette (utiliser `initialize`).
- **`--permission-prompts none` est incompatible avec la décision 7** : il retire `AskUserQuestion` (doc headless) et refuse tout ce qui demanderait une autorisation. Ne pas l'utiliser.
- **Blocs `thinking` vides** : seule `signature` est présente ; rien à afficher.
- **`--forward-subagent-text`** nécessaire pour reconstruire le texte des sous-agents d'avant-plan.
- **Pas de SIGINT sous Windows** : interrompre par le `control_request` `interrupt`, pas par un signal. SIGTERM laisse le tour inachevé (doc headless).
- **Flag non documenté** : `--permission-prompt-tool stdio` n'est ni dans `claude --help` ni dans la doc CLI (celle-ci ne décrit que l'outil MCP) ; il est lu dans le code du SDK et peut changer. Épingler la version du CLI et tester les `capabilities`.
- **Flux verbeux** : une ligne par fragment, y compris les fragments `partial_json` des outils ; lignes pouvant faire plusieurs ko (sortie du hook SessionStart) : lecteur de lignes sans limite fixe.
- **Coût du premier tour** : environ 0,17 $ sur le premier tour (création de cache de 20 000 tokens environ à cause des skills, hooks, MCP) ; `--bare` l'évite mais désactive skills et hooks.
- **Les outils lents du harnais** : un `sleep 40` en avant-plan est refusé par Claude Code, qui le relance en arrière-plan ; à ne pas confondre avec un blocage.

## 5. Choix d'implémentation : CLI brut, pas de SDK

Le SDK TypeScript (`@anthropic-ai/claude-agent-sdk` 0.3.325) n'est qu'une enveloppe : il lance le même binaire avec `--output-format stream-json --verbose --input-format stream-json` et parle le même protocole de contrôle. Il n'apporte rien d'indispensable pour ce périmètre. Il apporte des types, les callbacks `canUseTool` et hooks, des serveurs MCP in-process et la gestion de sessions ; les deux derniers devront être réimplémentés en Rust si le besoin apparaît (notamment pour l'outil MCP « formulaire », étape 2 de la décision 6). `.claude-work/reference/sdk.d.ts` sert de référence des types.

Licence : le paquet est sous « © Anthropic PBC. All rights reserved » avec renvoi aux conditions légales. Pour cette raison, `sdk.d.ts` n'est **pas versionné** : il reste en local dans `.claude-work/reference/sdk.d.ts` (dossier ignoré par git). Pour le retrouver : `npm pack @anthropic-ai/claude-agent-sdk@0.3.325`, puis extraire `package/sdk.d.ts`. Les références `sdk.d.ts:NNNN` de cette spec visent cette version.

## 8. Décisions prises en l'absence de l'utilisateur (à valider)

Choix faits pendant les jalons J4 à J12, sans l'utilisateur. Chacun donne la décision, sa raison et le moyen d'y revenir. Le code fait foi.

1. **Copie brute des sessions activée par défaut.** Chaque session copie son flux NDJSON dans `%LOCALAPPDATA%\orchestrator\logs\raw\*.ndjson`, plafonné à 50 Mo par session (`RAW_FILE_MAX`, la copie s'arrête avec une ligne `STDERR [orchestrator] …`) et 500 Mo au total (`RAW_DIR_MAX`, les plus anciens sont supprimés), 7 jours. Raison : fabriquer une fixture à partir d'un bogue réel (plan 1.9). Le fichier contient la conversation (contenus de fichiers, sorties de commandes) et reste local. Revenir : `ORCH_RAW_LOG=0` désactive la copie ; les plafonds sont deux constantes de `src-tauri/src/logging.rs`.
2. **Historique repris plafonné.** À la reprise, seuls les 20 derniers Mo du transcript sont relus ; chaque élément est tronqué à 64 ko ; un garde-fou borne la sortie à 25 Mo ; une notice « Début de l'historique omis (N lignes) » apparaît en tête du fil. Raison : un transcript de plusieurs centaines de Mo bloquerait l'interface. Revenir : constantes `max_bytes`, `max_item_bytes`, `max_output_bytes` de `src-tauri/src/sessions/transcript.rs` (20 Mo, 64 ko, 25 Mo).
3. **« Chat about this » envoie `replied_in_chat`.** Raison : c'est la valeur prévue par `sdk.d.ts` pour « répondre dans le chat ». En 2.1.325 Claude reçoit le même texte que pour `dismissed` et `skipped` (« The user did not answer the questions. »), prouvé par `question_live` (`t17`, `t18`) : la raison n'a aucun effet visible. Revenir : changer la `SkipReason` passée par `QuestionCard.svelte`.
4. **Rendu de la multi-sélection et des questions multiples inventé.** Le TUI n'a été capturé que pour une question simple (`07`) ; la multi-sélection (cases à cocher) et l'enchaînement de plusieurs questions sont dessinés par l'app dans le même style. Le tableau de labels est accepté par le CLI (`t16`). Revenir : capturer ces cas dans le TUI (hors du prototype 1) et aligner `QuestionCard.svelte`.
5. **Ctrl+C avec une carte de question ouverte** : interrompt pendant un tour, ne fait rien au repos. Raison : cohérence avec la décision 13 sans quitter la carte par accident. Revenir : le gestionnaire de touches unique (`keys.svelte.ts`), un cas testé.
6. **Ctrl+C au repos avec une saisie vide : ne fait rien**, alors que le TUI affiche « Press Ctrl-C again to exit » (`c3`). Raison : l'app ne se quitte pas au clavier dans le prototype 1 (décision 13). Revenir : ajouter le double Ctrl+C et l'indication.
7. **Palette** : Entrée envoie la commande telle quelle si elle n'a pas d'argument (ou si son nom est tapé en entier), sinon l'insère comme `/nom ` dans la saisie ; Tab l'insère toujours ; Ctrl+K sans correspondance affiche « No matching commands » et Entrée et Tab ne font rien. Raison : le TUI n'a été capturé que pour l'ouverture du menu (`10`). Revenir : `App.svelte` (choix de la palette), `Prompt.svelte` (clavier).
8. **Colonne des agents** : les agents terminés sont gardés (le TUI fait disparaître le panneau quand tout est fini), désormais rangés dans le panneau « ▸ N done » replié par défaut sous les agents vivants (décision 14 de la section 2) ; la durée et les tokens sont sur une deuxième ligne (colonne étroite) ; l'état de `main` est affiché. Raison : lisibilité d'une session à 4 agents. Revenir : `src/lib/components/agents/` (`AgentColumn.svelte`, `AgentCard.svelte`).
9. **`set_model` validé deux fois** : côté Rust (`validate_model`, `src-tauri/src/api/commands.rs` : `InvalidArgument` pour un modèle vide, commençant par `-` ou contenant espace ou caractère de contrôle) et côté interface (`validModel` dans `App.svelte`, message « Invalid model »). Raison : le modèle devient un argument de la ligne de commande ou une requête de contrôle. Revenir : retirer l'une des deux validations.
10. **Outils de développement sortis de l'installeur** : les binaires `probe`, `replay` et `fake_claude` sont dans un crate à part, `src-tauri/devtools` (`orchestrator-devtools`), et la dépendance `tauri` est compilée sans fonctionnalité (`features = []`). Raison : taille de l'installeur et surface d'attaque (< 15 Mo). Revenir : replacer les binaires dans le crate principal.
11. **Regroupeur d'événements** : bord avant (un lot part tout de suite quand aucun lot n'est parti depuis 16 ms, ou quand l'événement précédent date de 5 ms ou plus) et écho d'un message tapé jamais retenu (`4c41fd9`). Raison : latence mesurée en recette J12. Revenir : `src-tauri/src/state/batcher.rs`.
12. **`resume` n'accepte qu'un UUID** (déjà en 4.6) : règle de l'app, `InvalidArgument` sinon ; le CLI accepte aussi un nom ou un chemin. Revenir : assouplir `validate_launch_options`.
13. **Chemins réseau non vérifiés dans le sélecteur de projets** : un chemin UNC (`\\serveur\partage`, `//serveur/partage`) n'est pas testé (`is_dir` peut attendre le délai du réseau) ; il reste sélectionnable et `exists_checked` vaut faux (`src-tauri/src/sessions/list.rs`). Revenir : tester l'existence avec un délai.
